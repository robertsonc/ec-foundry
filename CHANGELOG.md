# Changelog

## 1.3.3 (2026-10-31)

- **`flowProcess` on Orchestrator 10.0.0**: `build` against a 10.0.0 Orchestrator failed `/validate` with `HTTP 400: Secure Web Services Config - Not valid value: flowProcess.` whenever a `secureWebServicesConfig` section was written for an appliance whose read has `urlClassificationConfig.flowProcess: null` (what Orchestrator 10.0.0.40724 reports for ECOS 9.7.2; verified with `/validate` probes: null and a missing key are rejected, `true`/`false` pass) or a non-boolean one. The 10.0.0 default template marks the key required (`true`: WebCC treatment of all requests, the default; `false`: first request only). The mapper now always writes it as a boolean: the appliance's value, `"true"`/`"false"` text as a boolean, or `true` with a `mapped` ledger line when the read has none and a `not-readable` line when the value is something else. A 9.x target still drops the key (not in its template). An all-default section read from a 10.0 appliance (which reports `flowProcess: true`) is now omitted like one from an older appliance, instead of being written because of that key. The null on a 9.7.2 appliance did the same: every such appliance got the section, and the 400, even with secure web services off.

## 1.3.2 (2026-10-28)

- **Routes with next hop 0.0.0.0 or :: lose their interface** (`docs/decisions/0016`): a local route (`localRoutes`, `segmentLocalRoutes`) with next hop `0.0.0.0` or `::` and a named interface is now written without `interfaceName`, whatever the source or target ECOS, and ledgered `mapped` with prefix, interface and segment. The interface has no effect, and ECOS 9.7+ rejects it on apply. The route's zone is written as the source has it; the appliance shows such a route with zone none (ECOS ignores a zone on a route without an interface), where the interface route showed the interface's zone. 1.3.0 left such routes out (ledgered unresolved) for a 9.7+ or unknown target ECOS, and kept the interface before 9.7. Two routes that become the same are written once, with a ledger line. `--target-ecos` is still accepted and recorded in `build.json`, `ledger.json` and `summary.md`, but no rule depends on it at present; the summary's unknown line says so.
- **Disabled NAC with only factory objects is left out**: an appliance with NAC off whose NAC holds only what ECOS creates (objects named `default`, a server at `0.0.0.1` or none with an empty key, trusted interfaces only) no longer gets a `nac` section, ledgered `default-omitted`. Written, it added a `nac_default_key` secret column and `/validate` rejected the empty key ("NAC - server key can not be empty"). NAC that is off but has any object of its own (a real server address, a key, an own profile or group, an interface policy) is written as before.
- **An empty NAC server key is caught before `/validate`**: `render` and `upload` now refuse a CSV row whose NAC server key column is empty ("secret column <col> is empty: fill it in the CSV (the toolkit never stores secrets)") and skip it, instead of sending it to Orchestrator, which rejects it. Only that secret is checked: other secrets (OSPF, BGP, tunnel keys) may be blank.
- **Which CSV to start from**: `build` now lists `<hostname>.csv` (empty sheet, headers only, for new sites) next to `example.csv` (this appliance's own values, secrets blank: copy it to start your `sites.csv`), and `columns.md` opens with the same two lines. No file is renamed.
- **Upload existing preconfig YAML files** (`docs/decisions/0017`): `validate --yaml FILE|DIR ... --orchestrator NICK` checks files (empty, not a mapping, not YAML or still Jinja: refused; `<SECRET:` placeholders: refused with their paths; Orchestrator `/validate`; name and serial conflicts) and never writes. `upload --yaml` makes the same checks and uploads every file that passes, with no `--approve` (the owner: "uploading a file is not dangerous; applying is dangerous and we are not doing it"), then reads the list back. Folders give their `*.yml`/`*.yaml` files; `--name` and `--serial` work with one file. A route with next hop `0.0.0.0`/`::` and an interface prints a warning. One line per file reports the outcome; a bad or conflicting file is skipped and the rest continue. `autoApply` stays false; the CSV path keeps `--approve`.

## 1.3.1 (2026-10-28)

Documentation only; the converter is unchanged from 1.3.0.

- **Skill guidance for 1.3.0 behaviour**: `SKILL.md` now tells the agent to ask for the target appliances' ECOS and pass `--target-ecos`, to lead its report with any `Warning: apply will fail` line, to name the route labels the target Orchestrator must already have and the interfaces the target must already have, and that `not-readable` also covers failed or malformed reads and sections withheld because a template group may provide them but its templates, or the template association, could not be read. The toolkit-error row now says a failure can hit one item or a whole section. It also notes that capture redacts credentials in free text.
- **README**: the `build` row names `--target-ecos` and what happens without it.

## 1.3.0 (2026-10-28)

Combines three changes that were open as separate pull requests (#4, #5, #6).

- **Code out of the skill folder** (`docs/decisions/0012`): `toolkit/` (`VERSION`, `scripts/`, `references/`) is the only source. The skill ships a copy made by `tools/build_skill.py`, which also rebuilds `dist/`. `tests/test_layout.py` fails while the copy or `dist/` differs from `toolkit/`.
- **Only keys the target template knows** (`docs/decisions/0013`): a preconfig holds a key path only if the target release's default template has it, or `TEMPLATE_OMISSIONS` lists it (10 paths `/validate` accepted on the corpus). Every dropped path is one `outside-preconfig` ledger line, and a dropped key never fails the build. This fixes `HTTP 400 Unrecognized field: "dot1x_acct_server_group"` from ECOS 9.5.x NAC.
- **ECOS 9.5.x payloads**:
  - The IP SLA and VRRP mappers no longer crash when `routeLabelId` or `tracker` is missing.
  - An HA group with `v6HaMask: 0` gets Orchestrator's default IPv6 pool.
  - A bonded `blanN`/`bwanN` with an empty speed counts as the default.
- **Capture**: reachability state 5 (sync in progress) counts as reachable, so live reads run.
- **Release families** (`docs/decisions/0014`): a release without its own default template uses the newest template of the same major.minor. Failing that, it uses the nearest older release (marked untested), then the nearest newer one. Only an empty template folder stops the build. `summary.md` and `ledger.json` (`default_template`) say which template was used and why.
- **Downloaded templates go to the work folder**: capture saves an Orchestrator's own default template in `<PRECONFIG_WORK>/reference/default-templates/`, never inside `toolkit/` or the skill. Template lookup searches both folders, and a bundled template wins over a download.
- **Lab replicate fixes**:
  - Capture redaction no longer reaches across a line break: an empty CLI secret (`authentication-key` with no value) used to replace the first word of the next running-config line with `<SECRET:text>`.
  - A segment whose OSPF is switched off but still configured on interfaces is written with `enable: false` instead of being dropped.
  - Lease times kept in the inactive DHCP server block of a relay interface are ledgered as outside-preconfig (the relay entry has no lease fields).
- **One bad item no longer drops its section**: list mappers (VRRP groups, BGP neighbors and segments, OSPF segments, local and segment routes, IP SLA rules, port forwarding, branch NAT rules, loopbacks, LAG and bridge groups, BFD, tags, multicast) skip an item they cannot read, ledger it as `toolkit-error` naming the item, and still write the rest. A section whose every item fails is not written, so a replace-on-apply section never goes out empty. The section-level catch stays as the outer net. NAT pools stay all-or-nothing: branch NAT rules refer to pools by list position. The "does this segment run BGP" probe is guarded too: a segment it cannot read is passed to the per-segment pass, which writes the others and ledgers it.
- **Item isolation, second pass** (review of the change above):
  - A list section whose every item fails is not written: multicast, BGP neighbors (default and per segment), local and segment routes, OSPF interfaces and areas. An empty list replaces the target's items on apply.
  - A null or non-dict item is skipped and ledgered like any other unreadable item; filters and ledger loops around the items (BFD, tags, bridge and LAG groups, segment OSPF) no longer trip on it.
  - Virtual tunnel interfaces, default-segment OSPF interfaces and areas, and each segment's OSPF interfaces are isolated per item.
  - Ledger lines name the item exactly: port-forwarding rules by their position in the captured list, branch NAT rules with their map name, segment BGP neighbors and segment routes under their own section. No "disabled" or "no tag has a name" note is written for items that failed.
  - A segment whose OSPF is switched off with no interfaces but keeps a router ID or redistribution map is ledgered as outside-preconfig (visible in summary.md) instead of default-omitted.
- **No silent drops found by the lab replicate**:
  - VXLAN VNI maps on a source with no VTEP interface are ledgered as outside-preconfig, naming each segment and VNI (the format requires `vtepSrcInterface`). They used to vanish without a ledger line.
  - Routes that could not be read are never written as an empty list (routes replace on apply). With `/subnets/all` unreadable (an unreachable appliance), the Default segment's routes come from `/subnets` and the other segments are left out and ledgered as not-readable. With `/subnets` unreadable too, `localRoutes` is not written and is ledgered the same way. A 403 still stops the capture (decision 0010).
- **Isolation, third pass** (second independent review):
  - A per-segment block that is present but null (routes, BGP neighbors, OSPF interfaces) is unreadable, not empty: the segment is ledgered and left out instead of written with an empty list. BGP settings that cannot be read while the segment has neighbors are a failure, not "no BGP".
  - With `/subnets/all` unreadable and no per-segment routes otherwise known, the non-Default segments are ledgered not-readable instead of "0 segments with routes".
  - A disabled OSPF segment is reported as keeping settings only for a redistribution map of its own: ECOS fills in a router ID on disabled segments and `default_rtmap_to_ospf` is the default.
  - Ledger accuracy: segment route notes name segmentLocalRoutes; no "mapped 0 segments" line; no localRoutes note pointing to a segment section that is not written; branch NAT priorities that are not numbers fail alone; VNI maps whose VTEP could not be read are not-readable, and VNI maps in an unexpected shape are unresolved. An empty multicast list in the source is written as before.
- **Reads that could not be done** (third independent review): an item whose source read failed is ledgered `not-readable` (check by hand), not `toolkit-error` and never "nothing configured". BGP enabled with an unread neighbors read, OSPF enabled with an unread interfaces read, a null segment's BGP settings, and a routes read without a table are left out and ledgered instead of written with an empty list. VNI maps are not-readable only when neither `/vxlan` nor the running-config was read. Numeric-id sorting never raises (tags, branch NAT priorities, VNI segments), and a branch NAT section whose every rule failed gets no "no rules configured" note.
- **Credentials in free text are redacted at capture**: a password written into a banner or other free text ("pass: x", "password = x", "PW: x", "passcode=x", and `"password":"x"` in JSON text inside a CLI line) is saved as `<SECRET:text>`. Also "secret = x", "psk: x", "token=x", "api-key: x". A quoted value is redacted up to its closing quote, a bare value after a quoted JSON key up to "," or "}", other free text up to whitespace; null/true/false and empty values are left alone; a quoted value stays on its line, single quotes count, and an unclosed quote is taken with the value. The free-text rules run before the CLI keyword rule. A CLI secret keyword followed by ':' or '=' is left to this rule instead of taking the separator as its value. Compound and camelCase key names are covered too: a quoted key whose name holds a keyed-field secret word (`"adminPassword"`, `"apiKey"`, `"client_secret"`, `{'password': 'x'}`, also CLI-escaped), as for fields, and an unquoted name that ends in one (`adminPassword: x`, `private_key=x`, `rsa-private-key: x`, `md5: x`; not `token-lifetime`, `pskType`, `md5sum`, `passwordless`). JSON numbers, true/false/null and a number after such a compound key are left alone, as field-level redaction leaves non-strings; a number after a plain secret word in prose (`password: 12345`) is still redacted. A value keeps its quotes, apostrophes and backslashes (`P@ss'w0rd!`, `Ab\cd9`, an escaped `\"` inside a JSON string) instead of being cut at them, after a quoted key the same kind of quote always opens the value (`{"password":",x"}`), and elsewhere a quote that ends a JSON string never opens a value, so a login prompt such as `{"banner": "Password: ", "motd": "x"}` keeps its next key and redacted JSON text, single or double encoded, stays valid with the same keys. A secret array (one level of nesting) becomes one placeholder item and an object is left to its own keys. The value patterns have no overlapping alternatives, so long runs of backslashes or quotes stay linear. Arrows (`password => x`) are caught; the prose fillers "is" and "-" only before a value holding a digit or symbol that is not trailing punctuation (`password is Abc123!`; `A password is required.` stays). Free-text credentials in banners or notes may not all be caught (for example `password is: x` or a value after an escaped quote); review captures before sharing them. A banner template on a test Orchestrator carried a demo login in clear, and capture saved it verbatim in the template-groups read. Field-level redaction was unchanged and covered keyed secrets only.
- **Template settings that do not apply are carried**: a `bgp` template whose `route_target_template` has `applyStatus: none` no longer owns the route targets. A `vxlan` template owns its fields one by one (`vtepIf`, VNI maps per segment): with `vtepIf` blank or `none` the appliance's VTEP interface, UDP port (required by `/validate`) and its other VNI maps are written; a template that sets the VTEP still owns the section. A `nac` template with `merge: true` still keeps the section out (`/validate` needs all six NAC lists, which only the template's objects fill), and the appliance's own NAC objects are now ledgered `outside-preconfig`.
- **Route labels resolve from route labels**: a local route's or IP SLA rule's `routeLabel` was looked up among the interface labels, which reuse the same ids, so a route on route label 1 was written null with no ledger line and an IP SLA rule could carry an interface label's name. Names now come from the appliance's route labels (`/cn/rtlabels` in the stored running-config); an id they do not name is written as null and ledgered unresolved, naming the route or rule and the id.
- **A contact only in the running-config is ledgered**: when the Orchestrator record has no contact but the running-config has `system contact ...`, the ledger says so (unresolved, with the value). It is not carried: the CLI holds one free-text string and `applianceInfo.contact` splits name, email and phoneNumber.
- **Route labels the target must have**: route labels are global Orchestrator objects like segments and interface labels, and /validate rejects a name the target lacks ("RouteLabel X doesn't exist"). summary.md lists the route labels a YAML names, and the validator name substitution (check --substitute) maps route labels too.
- **A malformed read never fails the whole translation** (`docs/decisions/0015`, owner rule: new or unexpected configuration runs with warnings, never errors): every independent block of the build reads its source in a guard. A read of an unexpected shape is ledgered `not-readable` (the whole read) or `toolkit-error` (one item) and skipped, and everything else is still written. This covers the appliance info (group, site, cluster profile, network role, region, location, contact), template groups and association, overlays, the system bandwidths and IPsec port, each interface and its DHCP and router-advertisement entries, DHCP failover, the HA groups and peer list, the label, segment, zone and role maps (also the mappers' copy), template field ownership and the stored backup's CLI lines. Replace-on-apply lists are never written short without a ledger line: an unreadable template association or overlay read leaves `templateGroups` or `businessIntentOverlays` out, and `deploymentInfo` is left out when `modeIfs` or a label, segment, zone or role map cannot be read or no interface entry could be read (interfaces are never invented or written empty). `haConfig` is all or nothing: it is not written when a WAN interface or a label it orders could not be read, or when no HA group lists the appliance. A name looked up through an unreadable map is never written as missing: list mappers (routes, IP SLA, port forwarding, ...) skip and ledger each item that needs it, and a section that needs it as a whole (segment routes, NAC server labels, VXLAN from the running-config) is ledgered not-readable and not written. With the template association unreadable, a section any template group selects is not written from the appliance. A DHCP failover block that failed to read is not reported as "no server has failover". An appliance or deployment read with no usable data still stops the build (nothing to convert).
- **A failed subnet-sharing read is not "no settings"**: when `/systemInfo/system` failed (HTTP 500 live and cached) or has another shape, local routes are still written but without subnet-sharing fields, and the read is ledgered not-readable for localRoutes and segmentLocalRoutes. It used to say default-omitted and "0 non-default segments with ... subnet-sharing settings" while the appliance had non-default sharing. A system-info read that was never captured is unchanged.
- **A read the capture could not make is not-readable, never empty**: build() checks the capture index for every read it consumes (template association and groups, overlays, groups, extra-info, cluster profiles, region, security maps, admin distances, running-config, HA groups, appliance list). A read with no usable live or cached copy (not a 404) is ledgered not-readable and nothing is written from it: no `templateGroups: []` that would detach every group on apply, no empty overlays, location or contact, no group written as its raw id. No stored backup is not-readable for the pass-through cap instead of a default claim, and VXLAN VNI maps without a readable backup are not-readable instead of "no VTEP". A DHCP server with failover on but no failover settings is ledgered. A readable HA group read that does not list the appliance keeps the 1.3.0 ledger.
- **An unread DHCP entry may want failover**: when an interface entry or its DHCP block could not be read, the interface counts as possibly having failover on, so no "no DHCP server there has failover enabled" line is written for it.
- **A name map with one bad item is unreadable**: a label, segment, zone or role object without a name (or of another shape) makes that map unreadable, so no name is written as null: `deploymentInfo` is left out and sections that need the names are not-readable. Mappers read the interfaces through the same check (NAC, port forwarding, multicast, IP SLA probes), so an unreadable `modeIfs` is not-readable there instead of a toolkit error, and no per-interface "toolkit bug" lines are added on top of an unreadable map. An interface label or zone id the maps do not name is ledgered unresolved (written as null, as before).
- **A null or odd subnet-sharing read is not "no settings"**: a `/systemInfo/system` read that came back null, or whose `auto_subnet` is not an object, is not-readable like a failed one. A read never captured, or an `auto_subnet` of null, still means no settings.
- **Interface readers see the same readability as build()**: NAC, port forwarding, multicast and IP SLA probes read the interfaces only when every entry is readable (an object with a numeric VLAN); otherwise their section is not-readable instead of a toolkit error. A region read of another shape is not-readable.
- **Template groups whose templates cannot be read**: when the association names groups but the template-groups read failed or has another shape, no section a template can provide is written from the appliance (not-readable, as with an unread association), so template-set fields are never written. The applianceInfo ledger line lists only the fields written; a cluster profile item that cannot be read is ledgered when the site's profile cannot be confirmed; a subnet-sharing read that is 404 everywhere counts as absent, like every other read.
- **A segment id that names no segment is never written as null**: an item in a vrf id that names no segment (a deleted segment, such as BFD left enabled in it) used to be written with `segment: null`, which Orchestrator applies to the Default segment (live: BFD was switched on in Default). Such an item is now skipped and ledgered unresolved ("vrf id N names no segment"): BFD, loopbacks, port forwarding, segment BGP, segment OSPF, segment routes, multicast, VXLAN VNI maps, virtual tunnel interfaces and branch NAT rules. NAT pools stay all or nothing (branch NAT rules refer to pools by position), so one such pool leaves `natPools` out.
- **Remote DHCP pool options are carried**: `/dhcpConfig/remoteSubnets` returns each option without its code, so `dhcpRemoteAddressPoolConfig.options` was left out (ledgered as an unmapped key). The code now comes from the stored backup (`/cn/dhcpd/config/subnet/<pool>/dhcp_options/<code>`) when the backup holds exactly the pool's option values; otherwise each option is ledgered unresolved, never guessed. A malformed option entry is ledgered and left out without losing the pool.
- **Multicast before ECOS 9.7 is carried**: the one-object multicast read of ECOS 9.5/9.6 (no `vrf_id`) was ledgered unresolved and not written. It is now written as the Default segment (ledgered as an assumption) with its enable flag, RP, filter and the PIM/IGMP settings of named interfaces; the virtual PIM interfaces `pimN` are ledgered runtime. An object with multicast off and nothing set is default-omitted instead of unresolved. A missing or odd multicast-enable read is ledgered not-readable, never taken as off.
- **Skipped Orchestrator-managed BGP neighbors are ledgered**: neighbors that Orchestrator services create (gms_marked) were left out without a ledger line; the ledger now names them (orchestrator-managed). The YAML is unchanged.
- **A dormant cluster interface is ledgered**: a stored backup with `cluster interface X` but no `cluster peer` lines writes no `flowRedirection` (unchanged) and is now ledgered default-omitted ("cluster interface X without peers (dormant)") instead of leaving no trace.
- **Management ports in interfaceConfig**: `interfaceConfig` never carries mgmt ports (the management plane stays as the target has it), but its default-omitted note claimed "every physical interface is admin up" while a mgmt port was down. The note now says every LAN and WAN interface, and an admin-down mgmt0 is ledgered outside-preconfig (other mgmt-port states, such as mgmt1 down, are the usual state and not ledgered).
- **Interface routes with next hop 0.0.0.0, and `--target-ecos`**: a static route with next hop `0.0.0.0` and a named interface passes `/validate`; apply rejects it on an ECOS 9.7.1 appliance ("Interface cannot be specified when Next Hop is 0.0.0.0") and applies it on ECOS 9.6.2.1, under the same 9.7.1 Orchestrator. The target appliance's ECOS decides, given with the new `--target-ecos` option of `translate.py` and `build` (kept in `build.json` for later rebuilds): 9.7 or later leaves the route out and ledgers it unresolved with prefix, interface and segment; before 9.7 keeps it; unknown (the default) leaves it out and says why and how to keep it. `--target-release` does not decide. `--target-ecos` accepts only an ECOS release (`9.6.2.1`, `9.6.2.1_107093`); anything else stops with an error, and a malformed value in `build.json` counts as unknown. Every translation records the ECOS it used: `target_ecos` in `ledger.json` (null when unknown), a "Target appliance ECOS" line in `summary.md` and in the translate output.
- **Warning for inline-router without both sides**: an inline-router deployment with no LAN (or no WAN) interface passes `/validate`, but apply rejects its deployment step. It is still written as the source has it, and is now ledgered unresolved and shown as "Warning: apply will fail" at the top of `summary.md` and in the translate output. EdgeHA WAN links count as WAN; a deployment with an unreadable interface is not judged.
- **OSPF only on interfaces the preconfig deploys**: OSPF interfaces were written straight from the source, including interfaces nothing in the YAML creates (bond members, interfaces with no deployment entry) and Orchestrator-managed loopbacks. `ospfSystemConfig` and `segmentOspfConfig` now write an OSPF interface only when it is a deployment interface (ifName or ifName.vlan), a user loopback or a user VTI; the others are ledgered unresolved, and gms_marked loopbacks and VTIs orchestrator-managed.
- **Interface references the preconfig does not create are ledgered**: BGP neighbor source interfaces, VRRP interfaces, route interfaces, the VXLAN VTEP interface and IP SLA source interfaces that name an interface the YAML does not create (no deployment entry, user loopback or VTI) keep the source value, since the target may have it, and are now ledgered: orchestrator-managed for a gms_marked loopback such as lo20000, unresolved otherwise. They used to pass silently. OSPF uses the same check (`carried_ifs`).
- **Missing PyYAML**: prints how to install it instead of a traceback.
